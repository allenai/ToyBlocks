Data generation

From a PDDL goal to a training set

You write down what should be true at the end of a task, for example "the red block is on the green block". The pipeline samples starting scenes, plans each episode with a TAMP (task and motion planning) planner, runs the plan on many simulated environments in parallel, checks every step, renders the result and writes a LeRobot dataset.

Tasks are goals

A ToyBlocks task is a PDDL problem: some initial facts and a goal written with predicates like on, on_table and ori_of (which face of a block points up and which way it's turned). The simulation environment and its reset states are generated from the problem, so adding a task means writing a goal, not writing simulation code.

The generators in scripts/task_gen/ produce whole task families:

GeneratorTasks
flip.pyTip a block over to a new face.
rotate.pyTurn a block about its vertical axis by one yaw step.
pnp.pyStack one block on another, or take it off onto the table.
stack_three.pyThree-block towers in scenes of 4–10 letter, digit and color blocks, with every letter readable at the end. Separate letter sets for training and validation. This is the generator behind the released training sets.
play_scene.py, search.py, find_as.pyScenes for play data and letter-search strategies (see below).

Block size, table height and friction can also vary from one environment to the next.

The TAMP planner

Demonstrations come from a task and motion planner. The task level works over the blocks PDDL domain and decides the order of skills: what has to be cleared, moved aside, flipped or rotated before the goal stack can be built. The motion level checks each step against the actual scene. Is there room to flip this block to the right, or is another block in its landing spot? Is the side the gripper needs to reach free? When a step is blocked, the plan gets extra steps to clear the way first, and the arm motions themselves come from cuRobo.

vecgen, the engine that runs data generation, is built on updated versions of our TAMP code, reworked so that planning and execution run batched across hundreds of environments.

Execution

Execution runs on vecgen, our vectorized engine. One Isaac Sim process per GPU holds hundreds of environments, and the skills (pick, place, flip, rotate and a few helpers) run as batched tensor operations on a pool of cuRobo inverse kinematics and trajectory optimization solvers. On a single GPU this gets up to 24× real time.

Checking every step

The TAMP planner plans each environment from its own state. After each skill, its effects are checked against the simulator. If the check fails, the environment goes back to a snapshot taken before the skill and tries again; if it keeps failing, the planner re-plans from wherever the scene is now. An episode only counts as a success if the goal actually holds at the end, and failed episodes are written to a separate split rather than mixed into the training data. Even on the hardest task families, 70–75% of episodes reach their goal.

Rendering

Physics and pixels are separate stages. Execution records what happened; rendering replays each episode and shoots it again with randomized lighting, HDRI backgrounds, table materials, exposure and camera poses. The robot's motion doesn't change, so one simulated episode can be rendered several different ways. Each render pass is a YAML file of flags, and a pass can produce several looks per episode.

Play data

Play data has no fixed task. Each environment starts from a reset state and keeps going: a goal policy looks at the current symbolic state and picks the next goal, the TAMP planner solves it, and the plan runs as batched vecgen skills. The scene isn't reset between goals, so each new goal starts from whatever the robot left behind. An environment keeps going until it hits a plan budget or a target number of successful plans, then moves on to the next reset state.

A few things you can control:

  • Skill balance. By default goals are chosen so the data comes out roughly a third pick-and-place, a third flips (spread over the four directions) and a third rotations (both directions). --no-balanced-skills switches to random goals.
  • Abandoned grasps. With --abandon-plan-percent, some pick-and-places are cut off partway through the carry. The next goal then drops the block and picks up a different one.
  • Search strategies. A DFA goal policy is a small YAML state machine that proposes goals until it accepts or rejects, for example flipping blocks until it finds a hidden letter. How to write one.

Play episodes are recorded the same way as regular datagen episodes, and go through the same render, merge and annotation stages. Episodes that reach their goal land in blocks_success, the rest in blocks_failure.

The dataset

The merge stage collects every problem into a single LeRobot v3 dataset. Annotation then adds two columns per frame: what the robot is doing, as text (for example pick), and where the target block is in the front camera image, projected from the recorded poses and camera parameters. Those are the inputs a two-level policy like Molmo 2 + ManiFlow is trained on.

Running it

This generates four stacking problems, runs 16 episodes of each, renders them and merges everything into one dataset:

python scripts/datagen/run_datagen_pipeline.py \
    --render-pass src/toyblocks/domain_randomization/flags/render_flags_allrand_texcache_glyphs_trainsplit_symmetric.yaml \
    --experiment-id my_run --output-root outputs \
    --task-gen-script scripts/task_gen/stack_three.py --task-gen-count 4 \
    --env-per-problem 16 --num-envs 16 --exec-num-envs 16 \
    --vecgen-problems-per-env 1

The stages run one at a time. Peak GPU memory we measured on one GPU:

StagePeak VRAM
Environment generation3.0 GiB
Execution, 16 to 256 environments5.4–6.3 GiB
Rendering, 8 environments9.6 GiB

So a 16 GB card is enough.
