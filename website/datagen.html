Data generation

From a PDDL goal to a training set

You write down what should be true at the end of a task, for example "the red block is on the green block". The pipeline samples starting scenes, plans each episode with a TAMP (task and motion planning) planner, runs the plan on many simulated environments in parallel, checks every step, renders the result and writes a LeRobot dataset.

Tasks are goals

A ToyBlocks task is a PDDL goal: which block should be on which, and which face should point where. The simulation environment and its starting scenes are generated from that goal, so adding a task means writing a goal, not simulation code.

Scenes are relations too

Starting scenes are written the same way: as relations between blocks, not coordinates. (on block_o block_y) stacks O on Y, (on_right block_red1 block_t) puts the red block against T's right side, and ori_of sets which face points where. Environment generation samples many concrete scenes from those facts, batched across environments. A block placed on the table is rejected if it overlaps another block, is out of the arm's reach, or leaves the front camera's view. After the physics settles, every fact is checked again, and the block is resampled if it doesn't hold. The table area blocks spawn in can be narrowed or split into separate regions, so training and test scenes can come from different parts of the table, the kind of split behind our spatial-generalization experiments.

The same predicates are then the goal the planner works toward, the labels in the recorded data, and what every eval checks step by step.

Task generators produce whole families of these goals: flipping a block to a new face, turning it, stacking one block on another, three-block towers in scenes of 4–10 letter, digit and color blocks (the family behind the released training sets), and scenes for play data and letter search. Block size, table height and friction can vary from one environment to the next.

The TAMP planner

Demonstrations come from a task and motion planner. The task level works over the blocks PDDL domain and decides the order of skills: what has to be cleared, moved aside, flipped or rotated before the goal stack can be built. The motion level checks each step against the actual scene. Is there room to flip this block to the right, or is another block in its landing spot? Is the side the gripper needs to reach free? When a step is blocked, the plan gets extra steps to clear the way first, and the arm motions themselves come from cuRobo.

vecgen, the engine that runs data generation, is built on updated versions of our TAMP code, reworked so that planning and execution run batched across hundreds of environments.

Execution

Execution runs on vecgen, our vectorized engine. One GPU runs hundreds of environments at once, and the skills (pick, place, flip and rotate) run batched across all of them. On a single GPU this gets up to 24× real time.

Checking every step

After each skill, its effects are checked against the simulator. If the check fails, the skill is retried; if it keeps failing, the planner re-plans from wherever the scene is now. An episode only counts if the goal actually holds at the end, and failed episodes are kept out of the training data.

Rendering

Physics and pixels are separate stages. Execution records what happened; rendering replays each episode and shoots it again with randomized lighting, HDRI backgrounds, table materials, exposure, and camera poses and intrinsics. The robot's motion doesn't change, so one simulated episode can be rendered several different ways.

Play data

Play data has no fixed task. A goal policy looks at the current scene and picks the next goal, the TAMP planner solves it, and the robot carries it out. The scene isn't reset between goals, so each new goal starts from whatever the robot left behind.

You can balance the skill mix (by default about a third pick-and-place, a third flips and a third rotations), cut some grasps off partway so the robot learns to recover, and script search strategies such as flipping blocks until a hidden letter turns up. Play episodes then go through the same rendering and labelling as everything else.

Every frame comes labelled

The planner knows what each part of a trajectory is for, so the labels come for free. Nobody annotates anything by hand.

Sub-goal segments

Every frame records which plan step the robot is carrying out (for example, moving block A onto block 4) and which motion phase it is in. The planner's symbolic state is recorded alongside. So each trajectory splits cleanly into one segment per sub-goal.

Target x, y in the image

Annotation projects the recorded block poses through the recorded front camera. That gives the pixel position of the block being acted on and of where it should go, on every frame, along with the action as text ("pick", "rotate cw" and so on).

What it lets you train

The text and the point are exactly what Molmo 2 learns to predict and what ManiFlow is conditioned on. The segment boundaries give ManiFlow its retract and "done" labels, which is how it learns to say when a skill is finished (play mode).

The dataset

The merge stage collects every problem into a single LeRobot v3 dataset. Annotation then adds the per-frame action text and target pixel positions described above, and the dataset is ready for training.
